# План исправления модели данных и продуктовой аналитики ЭнергоПульс

Дата фиксации: 2026-08-30.

Статус: утвержден к автономной реализации.

Режим исполнения: все задачи ниже имеют предварительное согласование. При
обнаружении технической неоднозначности выбирается вариант, который сохраняет
исходные данные, не скрывает расхождения и не меняет публичный API без
совместимого перехода. Вопросы, влияющие на бухгалтерское или договорное
значение показателя, не решаются молча: они фиксируются как `needs_review`.

## 1. Цель

Привести приложение к продуктовой модели, в которой пользователь работает с
утвержденными точками учета, а не с техническими секциями и строками Excel.

После реализации система должна:

- показывать 10 внутренних основных точек КОА;
- показывать внешнюю линию `ПС-110/35/6 кВ Южный Жанажол` отдельно;
- исключать двойной учет входов, отходящих линий и повторных счетчиков;
- корректно определять периоды ежедневных сводок по содержимому книги;
- использовать только одну активную версию набора на тип данных и период;
- учитывать акты потребления как отдельный коммерческий источник;
- рассчитывать полноту, среднее, пики и прогноз отдельно для КОА и
  субпотребителей;
- сохранять происхождение каждого показателя до файла, листа, строки и колонок.

## 2. Зафиксированный baseline

На текущих 19 загрузках подтверждено:

- все файлы распознаются, но все 19 имеют статус `ready_to_publish`;
- API фильтров пустой, потому что читает только `published`;
- июльская ежедневная сводка содержит 31 лист, но не получает период из-за
  отсутствия года в имени файла;
- в июньской сводке лист `27.07` содержит даты `26.06.2026` и `27.06.2026`;
- обе мартовские книги техбаланса дают одинаковые 589 staging-строк;
- июльский техбаланс возвращает 340 строк, но только 297 различных номеров ПУ;
- 41 номер ПУ встречается в техбалансе повторно;
- общий вход июля равен `8 119 634,91 кВт·ч`;
- сумма текущих 17 breakdown-групп равна `53 656 890,23 кВт·ч`, или 660,8% от
  общего входа;
- ежедневный breakdown формируется как одна группа `None`;
- 43 из 109 приборов июльского акта напрямую совпадают по номеру с приборами
  листа сторонних организаций техбаланса;
- параметры `station_id` и `substation_id` принимаются API, но не влияют на
  расчет;
- прогноз КОА и внешних потребителей делится по долям последнего месяца, а не
  рассчитывается как два самостоятельных ряда.

Этот baseline нужно оформить автоматическими regression-тестами до изменения
основных расчетов.

## 3. Продуктовые решения

### 3.1. Основные точки

В справочник входят 10 внутренних точек КОА.

Алибекмола:

1. `ПС 110/35/6 кВ Алибекмола`.
2. `ПС 35/6 кВ Северный Алибекмола`.
3. `ПС 35/6 кВ Южный Алибекмола`.
4. `ПС 35/6 кВ Газзавод-Алибекмола`.
5. `РП-6 кВ БКНС-Алибекмола`.
6. `РП-1 6 кВ ЦПНГ`.
7. `РП-6 кВ Газзавод`.

Кожасай:

8. `ПС 35/6 кВ Кожасай`.
9. `ПС 35/6 кВ БКНС-Кожасай`.
10. `РП-6 кВ Магистральная насосная`.

Внешняя граница, не входящая в число 10:

- `ПС-110/35/6 кВ Южный Жанажол`.

### 3.2. Источники истины

- Технический баланс определяет общий месячный вход, собственное потребление,
  внешний итог и технические границы.
- Ежедневная сводка определяет суточный профиль и оперативные точки нагрузки.
- Акт потребления определяет коммерческую детализацию по договору, потребителю
  и прибору учета.
- Значения трех источников не складываются. Между ними строятся сверки.
- Если коммерческий итог не совпадает с внешним итогом техбаланса, UI показывает
  расхождение и качество покрытия, но не исправляет данные молча.

### 3.3. Граница агрегации

- Для основной точки хранится отдельная утвержденная входная граница.
- Вход точки, ее отходящие линии и конечные счетчики нельзя суммировать в одной
  parts-of-whole диаграмме.
- Список 10 точек является каталогом узлов и не обязан суммироваться в общий
  вход, если точки находятся на разных уровнях одной сети.
- Процент от общего входа показывается только для взаимно исключающих потоков.
- Дочерние линии и приборы доступны через drill-down основной точки.

### 3.4. Публикация

Рекомендуемый MVP-вариант:

- файл без ошибок автоматически переводится в `published`;
- файл с предупреждениями остается `needs_review` до подтверждения;
- на сочетание `dataset_kind + period` существует одна активная опубликованная
  версия;
- новая версия после публикации помечает предыдущую как superseded;
- полностью одинаковое нормализованное содержимое блокируется как дубликат.

### 3.5. Пики

Начальная методика: P90 по выбранному периоду и выбранному сегменту. API должен
возвращать сам порог, метод `percentile_90`, объем выборки и период расчета.
Методика должна быть заменяемой на утвержденный фиксированный лимит без изменения
контракта фронтенда.

## 4. Целевая модель данных

Изменения выполнять в `apps/api/app/models.py` и новой Alembic-миграции в
`apps/api/alembic/versions/`.

### 4.1. Расширение `import_batches`

Добавить:

- `period_start: date | null`;
- `period_end: date | null`;
- `period_source: filename | workbook_header | user_override | null`;
- `content_fingerprint: string | null`;
- `supersedes_batch_id: int | null`;
- `superseded_at: datetime | null`;
- `is_active: bool`;

Индексы:

- `content_fingerprint`;
- частичная уникальность активной версии периода реализуется сервисной
  транзакцией и, где возможно, индексом БД.

### 4.2. Справочники

Добавить таблицы:

- `energy_sites`: `alibekmola`, `kozhasai`, external;
- `energy_points`: официальный узел ПС/РП;

- `meter_point_links`: связь ПУ с точкой и период действия;
- `balance_boundaries`: входные и выходные границы;
- `boundary_meter_links`: направление и роль прибора на границе;
- `mapping_candidates`: неизвестные или конфликтные связи.

Ключевые поля `energy_points`:

- `code`, `name`, `site_id`;
- `point_type: substation | distribution_point | external_supply`;
- `ownership: koa | external`;
- `parent_point_id`;
- `active_from`, `active_to`.

### 4.3. Факты

Добавить `consumption_facts`:

- `import_batch_id`, `dataset_kind`;
- `period_start`, `period_end`, `granularity`;
- `energy_point_id`, `meter_id`, `boundary_id`;
- `value_kwh` как `Numeric`, не `float`;
- `flow_role: inflow | outflow | internal | consumer | loss`;
- `ownership_segment: koa | subconsumer | external_supply | unknown`;
- `calculation_method`;
- `quality_status`;
- `source_sheet`, `source_row`;
- `source_columns`, например `F,G,E`;
- `raw_value`, `reported_value`, `difference_kwh`.

## 5. Backend: порядок реализации

### Этап A. Период, даты и версии

Основные модули:

- `apps/api/app/services/ingestion.py`;
- `apps/api/app/services/dashboard.py`;
- `apps/api/app/main.py`;
- `apps/api/app/models.py`;
- новая миграция Alembic.

Действия:

1. Вынести определение периода из `dashboard.py` в новый модуль
   `apps/api/app/services/periods.py`.
2. Реализовать `extract_daily_sheet_date(cells, sheet_name)`.
3. Для ежедневного листа брать конечную дату интервала из строки заголовка,
   обычно колонка G строки 2.
4. Сверять дату заголовка с `DD.MM` имени листа.
5. Имя файла использовать только для проверки и fallback.
6. Добавить issues:
   - `PERIOD_NOT_DETECTED`;
   - `SHEET_DATE_NAME_MISMATCH`;
   - `SHEET_OUTSIDE_BATCH_PERIOD`;
   - `MISSING_DAILY_SHEET`;
   - `DUPLICATE_DAILY_DATE`;
   - `DUPLICATE_DATASET_CONTENT`;
   - `PERIOD_VERSION_CONFLICT`.
7. Рассчитать semantic fingerprint из типа набора и нормализованных значимых
   ячеек, исключая оформление и workbook metadata.
8. Централизовать выбор данных в `active_batches_query()`.
9. Удалить различия, при которых фильтры читают `published`, а дэшборды
   `ready_to_publish`.

Критерии этапа:

- июль определяется как `2026-07` без переименования файла;
- лист `27.07` июньской книги обрабатывается как `2026-06-27` и получает issue о
  несовпадении имени;
- в июне 30 дней, в июле 31 день;
- март присутствует во временном ряду один раз;
- `/api/v1/filters` возвращает январь-июль и активные справочники.

### Этап B. Нормализация точек и счетчиков

Создать:

- `apps/api/app/services/energy_catalog.py`;
- `apps/api/app/services/mapping.py`;
- seed-функцию для 10 точек и внешней линии.

Порядок mapping:

1. точное совпадение нормализованного номера ПУ;
2. действующая связь `meter_point_links`;
3. точный alias заголовка;
4. нормализованный alias;
5. mapping candidate со статусом `unresolved`.

Не использовать ближайший заголовок как окончательную бизнес-классификацию.
Текущий `technical_context_for_row()` можно оставить только как extractor hint.

Первые aliases формируются из реальных заголовков, включая:

- `ПС-110/35/6кВ` -> `ПС 110/35/6 кВ Алибекмола`;
- `ПС 35/6 "Северная"`, `ПС Север` -> Северный Алибекмола;
- `ПС 35/6 кВ "ЮЖНАЯ"`, `Юг` -> Южный Алибекмола;
- `ПС35/6кВ "Газзавод Алибекмола"` -> Газзавод-Алибекмола;
- `РП -1 6кВ "ЦППНГ"` -> РП-1 ЦПНГ;
- `П/С 35/6 "Кожасай"` -> ПС Кожасай;
- `П/С 35/6 "БКНС Кожасай"` -> БКНС-Кожасай;
- `РП 6кВ "Насосная перекачки"` -> Магистральная насосная.

Для БКНС-Алибекмола и РП Газзавод mapping строится по входным приборам и
границам, поскольку отдельный стабильный заголовок присутствует не во всех
секциях.

### Этап C. Извлечение фактов

Разделить текущий монолит `apps/api/app/services/dashboard.py`:

- `technical_balance_facts.py`;
- `daily_consumption_facts.py`;
- `commercial_consumption_facts.py`;
- `energy_metrics.py`;
- `forecast.py`.

Технический баланс:

- сохранять физические строки ПУ один раз на источник;
- повторное появление того же ПУ в другой секции сохранять как lineage/reference,
  но не как новый физический расход;
- отдельно извлекать входные boundary facts и дочерние outflow facts;
- не агрегировать все 340 строк в breakdown.

Ежедневная сводка:

- определять активную точку по mapping ПУ, а не по переменной
  `active_substation = None`;
- рассчитывать controlled input по утвержденным входам;
- классифицировать точки нагрузки как КОА, субпотребитель или unknown;
- сохранять один daily fact на дату, прибор и роль.

Акт потребления:

- читать одновременно формулу и cached value для `.xlsx`;
- извлекать договор, потребителя, номер ПУ, показания и коэффициент;
- независимо рассчитывать базовое потребление `(G-F)*I`;
- сохранять коммерческую надбавку/потери отдельно от базового потребления;
- сопоставлять с ежедневными и техническими фактами по номеру ПУ;
- строить сверку акта с внешним итогом техбаланса.

### Этап D. API

Обновить endpoints в `apps/api/app/main.py`.

`GET /api/v1/catalog/energy-points`:

- возвращает 10 внутренних точек и внешнюю линию;
- поддерживает `site`, `point_type`, `ownership`, `query`.

`GET /api/v1/dashboards/technical-balance`:

- `points`: основные точки с входом, качеством и drill-down count;
- `boundaries`: только совместимые агрегаты;
- `table`: строки ПУ с lineage;
- `unresolved_mappings`;
- не возвращает произвольный top-10 как список подстанций.

`GET /api/v1/dashboards/daily-consumption`:

- даты в ISO `YYYY-MM-DD`;
- `coverage: actual_days, expected_days, percent, missing_dates`;
- `segments: koa, subconsumers, unknown`;
- breakdown по каноническим точкам;
- среднее и пики на backend.

`GET /api/v1/dashboards/peaks`:

- фильтры `period`, `point_id`, `segment`;
- `average_daily_kwh`;
- `peak_day`;
- `threshold_value`, `threshold_method`, `sample_size`;
- события превышения и резких изменений.

`GET /api/v1/dashboards/energy-business`:

- только уникальные активные периоды;
- фильтры реально ограничивают факты;
- `own + subconsumers = total` только на одной утвержденной границе;
- предупреждение о доле unknown mapping.

## 9. Definition of Done

Работа считается завершенной, когда одновременно выполнены условия:

- отображаются 10 внутренних точек КОА и отдельно внешняя линия;
- в продуктовых breakdown нет технических заголовков вместо основных точек;
- один физический ПУ не удваивает потребление;
- июль имеет 31 день, июнь 30 дней;
- март присутствует один раз;
- периоды и справочники доступны в фильтрах;
- фильтры изменяют фактические расчеты;
- полнота показана как факт/ожидание и процент;
- среднее и пороги рассчитаны отдельно для КОА и субпотребителей;
- акты используются в коммерческой детализации и сверке;
- прогнозные сегменты рассчитаны независимо и сходятся с общим прогнозом;
- каждое значение имеет lineage;
- backend tests, frontend build и browser smoke проходят;
- `docs/IMPLEMENTATION_JOURNAL.md` обновляется после каждого реализованного
  feature-level этапа без секции со списком файлов.

## 12. Правила автономной работы

1. Перед каждой миграцией делать read-only snapshot схемы и проверять downgrade.
2. Перед преобразованием данных запускать smoke на копии, не на исходной папке
   `данные/`.
3. Любое исправление классификации делать через mapping/alias или seed, а не
   через точечный хардкод в дэшборде.
4. Любое изменение API сопровождать тестом на результат фильтра и обратной
   совместимостью ответа, если endpoint уже используется frontend.
5. Любой финансовый показатель без утвержденной границы помечать как
   неподтвержденный и не использовать в официальном KPI.
6. После каждого завершенного W-этапа обновлять этот документ, тесты и журнал;
   в конце сессии оставлять короткий отчет о сделанном, проверках и блокерах.

## 13. Порядок автоматического продолжения

Исполнение идет последовательно: `W0 → W1 → W2 → W3 → W4 → W5`. Внутри
этапа независимые тесты, документация и read-only диагностика выполняются
параллельно. Нельзя переходить к следующему этапу, если его критерий выхода
не подтвержден тестом или воспроизводимым smoke-отчетом.
